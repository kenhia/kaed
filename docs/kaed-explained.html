kaed — ken's agent editor

An editor whose only user is a machine.

Every feature of a normal editor — the viewport, the cursor, the undo stack — exists to serve eyes and fingers. An agent has none of those. kaed is what an editor looks like when you design for the client that actually shows up: one that can't see the screen, whose copy of the file is always slightly out of date, and that pays for every byte you hand back.

version — blake3(file bytes)[..16] 7e6a34a06119ff41

The problem

An agent on one machine, files on another

That's the whole problem, and it turns out to be badly served. The two obvious approaches both fail — and they fail quietly, which is the expensive part.

whole-file only

Piping over ssh

Base64 makes it quote-safe, but it's whole-file replace — no surgical edits. Every write needs a manual checksum round-trip to confirm it landed.

Agents skip that verification. It costs a turn, and it usually passes.

reports success

Mounting the filesystem

Native tools work, which is the appeal. But edits strip the executable bit, and a hard kill corrupts the cache — after which writes fail while the editing tool still reports success.

Changes made on the far side hide behind a directory cache. Silent data loss here is a lived experience, not a hypothetical.

Both are human file-access machinery pressed into agent service. Neither was designed for a client that can't look at the result.

The core loop

Verified writes

One round-trip instead of three. The agent never re-reads a file to find out what its own edit did.

01

Read or search

Every response carrying file content also carries that file's version.

"version": "060ad669c1a1d257"
02

Edit, declaring the base

The mutation names the version each file was computed against. All ops land, or none do.

base: [{ path, version }]
03

Take the diff as proof

The response contains exactly what changed on disk, plus the new version. Nothing to verify.

"applied": true
edit response — the proof 060ad669c1a1d257 → 7e6a34a06119ff41 
--- a/app/main.rs
+++ b/app/main.rs
@@ -1 +1 @@
-let pw = env("DB_PASSWORD");
+let secret = env("DB_PASSWORD");

When the file moved on

If the declared version doesn't match what's on disk, the edit is refused — and the error carries a diff of what changed since you looked, so the agent can re-anchor and retry without re-reading.

A version is the hash of the bytes, computed on demand and stored nowhere. That makes it a content address, not a session handle: it never expires, and it survives client restarts, server restarts, reconnects, and credential rotation. An agent resuming after a crash can edit straight from a version it recorded an hour ago.

Architecture

One daemon per host

kaed owns the mechanics of editing on the machine it runs on and exposes them as MCP tools over HTTP. It binds loopback; a tunnel handles transport and network access.

Blast radius

Three layers, deliberately unequal

The first deployment rooted at $HOME. Within a day, a remote agent read the bearer token that gated the service — out of kaed's own config directory, through kaed. This is what came of that.

kaed's own directories

Its config and journal paths are refused before any configuration is consulted, so kaed can never serve or rewrite the credential that gates it.

not configurable — by design

Default deny globs

.ssh, .gnupg, .aws, .netrc, .git-credentials and friends — credential stores, matched against a path and every one of its ancestors. Secret-bearing files (.env*, *.pem, id_*) are deliberately not here: they classify instead — served redacted or refused as opaque, edited through typed ops — because a file agents can never touch is a file agents route around.

on unless you turn them off

Whatever else you name

Project-specific globs from config. Additive only. A root that lands inside a denied area is refused at startup rather than silently serving nothing.

yours

Refusal is never silent

Addressing a denied path returns denied — permanent, and distinct from "you got the path wrong", because no correction makes it work. Listings and searches omit denied entries instead of failing, but report denied_hidden: 2 alongside the results. A filtered listing that doesn't say so reads as a complete one.

The operating system refuses too, and it never read your config. A file the service identity can't open comes back as denied with not_readable_by_service_identity, the owning uid and mode, and the uid kaed runs as — the difference between "chmod this" and os error 13. Listings count those in unreadable_hidden: one unreadable directory should never decide the fate of an entire search, and for one sprint it did.

Stated plainly: this is blast-radius reduction, not access control. Any agent with a shell can read what kaed refuses to serve. What the deny list buys is that the ordinary, well-intentioned path is safe — a grep doesn't hoover up credentials by accident, and a careless edit can't rewrite your authorized_keys.

Deployment

One instance per machine, one front door

Each host runs its own daemon with its own roots, its own journal, and its own tokens. Nothing is shared, so nothing has to agree. Roots are named for the machine that serves them — kai:src — and each daemon also states which hosts are supposed to be running one, so a machine deliberately left out never looks like a rollout that failed.

On top of that independence, one host acts as the gateway. A call naming another host's root is forwarded to that host's daemon and journaled there — under the caller's own identity, using a credential issued to that caller for that host. No shared state and no impersonation: a caller without a credential for the target is refused, never proxied as someone else. The gateway is a convenience, not a dependency — every daemon still answers at its own URL.

The reason to bother is the client. Tool definitions are context an agent pays for, so three hosts wired directly would mean three MCP servers and three copies of every tool schema in the agent's window. Through the gateway it is one connection and twelve tools no matter how many machines join — the root name already says where the work happens.

Where it stands

Early beta, and honest about it

Twelve tools — roots, stat, list, read, search, edit, history (diff, journal, revert), feedback, and a secret lifecycle (secret, secret_reveal) — working end to end from a remote agent, on three hosts, used every day by the person who wrote it and essentially nobody else.

shipped Walking skeleton. The first six tools, versioned reads, atomic apply, the journal, bearer auth over streamable HTTP. Deployed and verified from a remote agent.
shipped Blast-radius hardening. Everything the first live test exposed: the deny list, self-describing 401s, failed transactions in the journal, real blob retention, non-breaking token rotation.
shipped Fleet deploy. One published bundle in a package store; every host installs that. Three hosts, no checkout or toolchain on two of them.
shipped History tools. journal, diff, revert — the data was already being written; now it reads back through the contract, plus a feedback tool wired into every error.
shipped Secrets. Dotenv files are classified, not denied: served redacted, edited through typed ops, rotated by a lifecycle that never hands the agent a value — and writes elsewhere are scanned so a known secret can't quietly land in an ordinary file.
shipped Gateway. One connection reaches the fleet: a call naming another host's root is proxied under the caller's own identity and journaled on the host that serves it — never impersonated, never silently rerouted.
next Structure. Tree-sitter outlines, node-targeted edits, and parse diagnostics returned in the edit response — so "did I break the syntax?" is answered by the write, like everything else.
the test The dogfood report. A usage report now exists — every call journaled, analyzed, re-runnable from the journal itself. The head-to-head against ssh-piping and mounts (round-trips, failures, token cost) is still owed; until then, "kaed is better" is a hypothesis.
